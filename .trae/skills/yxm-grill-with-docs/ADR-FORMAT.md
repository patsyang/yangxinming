# ADR 格式

ADR 放在当前 skill 约定的输出目录的 `adr/` 子目录中，并使用顺序编号：`0001-slug.md`、`0002-slug.md` 等。

只在第一个 ADR 真正需要时创建 `adr/` 目录。

## 模板

```md
# {决策短标题}

{1 到 3 句话：背景是什么，决定了什么，为什么这样决定。}
```

这就够了。ADR 可以只有一个段落。价值在于记录“做过这个决策”以及“为什么这么决策”，而不是填满固定章节。

## 可选章节

只有在确实增加信息价值时才加入这些章节。大多数 ADR 不需要。

- **状态** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）- 适合决策可能被重新讨论的场景
- **备选方案** - 只有被拒绝的替代方案值得未来记住时才写
- **影响** - 只有存在不明显的下游影响时才写

## 编号

扫描 `adr/` 目录中的最大编号，并在此基础上加一。

## 什么时候创建 ADR

必须同时满足以下三个条件：

1. **难以逆转** - 未来改变主意的成本有实际意义
2. **缺少上下文会显得意外** - 未来读者会疑惑“为什么要这么做”
3. **存在真实取舍** - 确实有替代方案，并且因为具体理由选择了其中一个

如果一个决策很容易逆转，就不要写 ADR；以后直接改即可。如果它并不意外，就不会有人追问原因。如果不存在真实替代方案，也没有必要记录“我们做了显而易见的事”。

### 什么内容适合写 ADR

- **架构形态。** 例如“使用 monorepo”“写模型采用事件溯源，读模型投影到 Postgres”。
- **上下文之间的集成模式。** 例如“订单和计费通过领域事件通信，而不是同步 HTTP”。
- **带有锁定成本的技术选择。** 例如数据库、消息总线、认证提供方、部署目标。不是每个库都要写，只记录未来替换成本很高的选择。
- **边界和范围决策。** 例如“客户数据由客户上下文拥有，其他上下文只能按 ID 引用”。明确的“不做什么”和“做什么”同样重要。
- **有意偏离显而易见路径的决策。** 例如“因为 X 使用手写 SQL 而不是 ORM”。这类记录可以避免未来的人把有意取舍误认为待修复问题。
- **代码中不可见的约束。** 例如“因为合规要求不能使用 AWS”“因为合作方 API 合同要求响应时间低于 200ms”。
- **拒绝理由不明显的替代方案。** 如果曾考虑 GraphQL 但因为微妙原因选择 REST，就记录下来；否则六个月后可能又有人重新提出 GraphQL。
