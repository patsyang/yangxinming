# AI Native 评审 Lens

当计划涉及 Agent、AI 助手、自动化任务、LLM 工作流、工具调用、知识库、模型推理或自主决策时，`plan-ceo-review` 必须额外使用本 lens。

目标不是把传统功能包装成 AI Native，而是判断 AI 是否真的增加了杠杆，以及风险是否被产品化处理。

## Agent 适用性

先判断是否真的需要 AI / Agent：

- 是否需要结合上下文做复杂判断。
- 是否规则越堆越乱，传统规则系统维护成本过高。
- 是否需要理解非结构化输入，如文本、图片、语音、网页、文档或对话。
- 是否需要跨工具执行任务，而不是只给建议。
- 是否存在足够容错空间，允许模型不确定性被流程吸收。

如果简单表单、固定规则、脚本、RPA 或传统 CRUD 就能稳定解决，应降低 verdict，优先建议非 Agent 方案。

## AI Native 硬问题

评审时必须回答：

1. Agent 要替用户完成什么结果，而不是展示什么能力。
2. Agent 何时触发：对话、事件、定时、API、人工按钮还是后台监控。
3. Agent 需要读取哪些上下文、知识、历史记录和业务数据。
4. Agent 可以调用哪些工具或 API，哪些工具只读，哪些能写回。
5. 哪些动作可以自动完成，哪些必须人工确认。
6. Agent 如何解释自己的依据、置信度和不确定性。
7. 失败时用户看到什么，系统如何降级、重试、回滚或转人工。
8. 如何评测质量，如何防止建议抖动、重复建议和无意义优化。
9. 成本、延迟、上下文窗口和模型选择是否影响产品体验。
10. 安全、权限、PII、提示注入和工具误用是否有边界。

## 必须暴露的边界

AI Native 计划至少要写清：

- `Autonomy Boundary`：自动执行到哪一步，哪里必须停。
- `Tool Boundary`：可调用工具、读写权限、失败处理。
- `Context Boundary`：可用知识、记忆、数据来源和过期策略。
- `Human Control`：审批、撤销、接管、争议处理。
- `Evaluation Loop`：离线评测、线上指标、人工抽检、回归样例。
- `Trust Surface`：用户如何理解、检查和纠正 Agent 输出。

缺少这些边界时，不得输出 `APPROVE`。

## 常见失败模式

- 把“AI 总结 / AI 推荐 / 智能化”当成价值本身。
- 没有明确用户任务，只展示模型能力。
- 自动化边界过宽，高风险动作没有人工确认。
- 工具调用失败、数据缺失、知识过期时没有兜底。
- 没有评测集，只用主观“效果不错”判断质量。
- 没有观测和审计，无法追踪 Agent 为什么做出某个建议。
- 成本和延迟没有进入产品决策。
- 用传统 PRD 写功能点，遗漏模型、工具、上下文、评测和失败处理。

## 结论调整

- 如果 AI 不是必要条件，优先建议传统方案或 `REDUCE_OR_KILL`。
- 如果 AI 价值成立但边界不清，输出 `REQUEST_REVISION`。
- 如果高风险自动化缺少审批或回滚，输出 `DEFER` 或 `KILL`。
- 如果 Agent 价值、边界、评测和风险处理都清楚，可进入普通投资门继续评审。
