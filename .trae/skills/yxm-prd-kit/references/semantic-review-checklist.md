# Semantic Review Checklist

用于 W7、W9、W10 前的语义反思。它不是格式检查，而是发现文字、概念、对象、流程和用户纠错吸收层面的错误。

## 必查项

- 用户明确否定过的内容是否被重新引入。
- 同一菜单、对象、字段、动作、状态在不同章节是否含义一致。
- 用户概念是否和内部技术概念混写，例如把用户看到的“报告清单”写成内部 manifest。
- 表格字段是否真的属于对应实体。
- 需求、流程、对象模型、状态机和验收标准是否互相对齐。
- 删除、终止、暂停、取消、失败、重试、过期等高风险动作是否定义清楚。
- 正式 PRD 是否包含过程语言、运行时字段、质量门说明或未闭合阻断项。
- 是否存在为了完整性而引入的过度设计。

## 阻断条件

命中以下任一情况，不允许进入下一阶段：

- 存在用户已否定内容的回流。
- 存在同一对象在不同章节含义不同。
- 存在 high 或 critical 未关闭质疑。
- 存在未处理冲突。
- 正式 PRD 中出现内部运行时术语或过程字段。
- 验收标准无法测试。
- 正式 PRD 出现泛泛的“用户可以”但无法映射到用户模型。
- 正式 PRD 将关键业务流程退化成 CRUD 或按钮级功能流程模板。
- 正式 PRD 中关键业务流程缺少业务目标、参与用户、业务结果、对象状态或验收映射。
- W10 前有效问题 quota、阶段覆盖或视角覆盖未达标。
- 存在未闭合 Repair Loop issue，或 repair_applied 后未 root_stage_revalidated。
- W9 前缺少真实重读记录。
- W9 前正式 PRD 必选章节缺少章节级语义 challenge，且没有逐章节 waiver。
- W10 CEO 评审缺少可回灌的 passed 或 changes_requested 结论。
- `evidence` adapter 缺少 evidence provenance。

## 输出到过程文件

```text
## 语义反思记录
| 时间 | 阶段 | 结论 | 必须修复项 | 已处理 |

## 真实重读记录
| 时间 | 阶段 | artifact | path | 结论 | status |

## W9 章节语义质疑覆盖记录
| 章节 | challenge_id | source_adapter | 结论 | status | waiver_id |
```

`必须修复项` 为空或 `无`，且 `已处理` 为 `是`、`true`、`closed` 或 `completed` 时，才视为通过。

## W9 Readiness Gate

W9 输出正式 PRD 前必须完成真实重读和逐章节语义 challenge：

1. 重新读取过程文件、正式 PRD 草稿和用户关键原话来源，并在 `真实重读记录` 中记录 `process_file` 与 `formal_prd`。
2. 对 `prd-kit.wf` 中 `output_rules.when_pass.required_sections` 的每个章节至少提出一个语义 challenge。
3. challenge 必须覆盖口径、对象、状态、边界、数据来源、验收或例外场景，不允许只问标题和格式。
4. 每个章节的 challenge 必须写入 `W9 章节语义质疑覆盖记录`；若用户明确豁免，必须引用 `Adapter Waiver Ledger` 中的 `waiver_id`。
5. 过程文件、正式 PRD 与用户原话存在不一致时，必须写入冲突账本；不得只在回复中口头说明。

## 用户和业务流程语义检查

- 检查正式 PRD 中每个用户称谓是否能映射到用户模型账本。
- 检查每个用户是否有能做什么、不能做什么、数据边界和与其他用户的关系。
- 检查每条关键业务流程是否保留业务闭环，而不是只列页面动作。
- 检查关键业务流程是否映射对象状态和验收标准。
- 检查 repair 问题是否真正回到 root_stage 深挖，而不是在后置阶段顺手改文案。
