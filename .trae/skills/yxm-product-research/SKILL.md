# 产品研究助手

## 概览

通用的产品/公司研究自动化工具。输入任意公司或产品的官方网站 URL，自动完成从信息采集到研究报告输出的全流程。

**核心能力**：
- 🔗 **静态入口发现** — 自动发现并分类官网关键页面
- 🖼️ **上下文优先图片分类 v2.5** — 基于来源页、区域标题、截图类型、尺寸和视觉质量筛选架构图/功能图/方案图
- 📄 **文档自动下载** — 自动识别并下载白皮书/案例/产品手册等文档
- 🌐 **Agent Browser 动态采集** — 使用真实浏览器渲染、滚动、抓取图片候选和页面截图
- 📊 **结构化报告生成** — 按照标准模板输出完整的产品研究报告

---

## ⚠️ 核心约束（执行前必须阅读）

### 报告结构的绝对强制要求 ⚠️⚠️⚠️

**最终输出的研究报告必须且只能包含以下 11 个一级章节，顺序不可改变、不可合并、不可省略：**

```
一、公司概况        （含创始人/团队信息）
二、核心定位        （产品定位/Slogan/价值主张）
三、目标市场        （目标客户分析）
四、场景痛点        （解决的场景与痛点）
五、产品架构        （技术架构/功能架构/部署架构）
六、功能特性        （主要功能特性）
七、差异化优势      （技术/功能等优势）
八、解决方案        （场景方案/行业方案）
九、典型案例        （客户案例介绍）
十、竞品清单        （竞争性产品分析）
十一、关键发现      （总结与洞察）
```

**铁律（违反即视为任务失败）：**
1. ✅ **11 个章节必须全部存在**，一个都不能少
2. ✅ **每个章节必须有实质内容**，禁止出现只有标题 + 一句话的情况
3. ✅ **章节顺序严格按上述排列**，不得自行调整
4. ✅ 如果某章节确实找不到相关信息 → 写明"经多方检索暂未找到相关公开信息"，并说明尝试过的途径，**绝不能直接跳过该章节**
5. ✅ 每个章节至少应包含 **2-3 个段落或有意义的子节**，总字数建议不少于 200 字/章

## 阶段 1：准备阶段

### 步骤 1.1 解析用户输入

确认用户提供的信息：
- **目标 URL**：公司/产品官网地址（必填）
- **研究重点**（可选）：用户特别关注的方面
- **输出目录**（可选）：默认为当前工作目录下的 `output/pat-product-research/<公司名>/<research-version>/`

### 步骤 1.2 初始化工作目录

创建以下标准化目录结构：

- 根目录固定为 `output/pat-product-research/`
- 公司目录固定为 `output/pat-product-research/<公司名>/`
- **每次研究必须创建全新的版本目录**：`research-YYYYMMDD-HHMMSS`
- **当前研究只允许读取和写入当前版本目录**
- **禁止读取旧版本目录中的 pages/images/documents/output/temp 作为本次输入**
- **禁止修改旧版本目录中的任何文件**

```
output/pat-product-research/
└── <公司名>/
    └── research-YYYYMMDD-HHMMSS/
        ├── output/              # 最终产出
        │   └── 产品研究_<公司名>_<YYYYMMDD>.md
        ├── pages/               # 页面快照（HTML→MD）
        ├── images/              # 有价值的图片
        │   ├── architecture/
        │   ├── feature/
        │   ├── solution/
        │   ├── other/
        │   └── _review_pending/
        ├── documents/           # 文档资料
        │   ├── whitepaper/
        │   ├── case/
        │   ├── brochure/
        │   └── other/
        └── temp/                # 临时文件（完成后可删除）
```

### 步骤 1.2.1 版本隔离规则

每次新研究必须：

1. 先确定公司目录 `output/pat-product-research/<公司名>/`
2. 生成新的 `research-YYYYMMDD-HHMMSS/`
3. 只在该目录下创建和读取 `output/ pages/ images/ documents/ temp/`

禁止行为：

1. 读取旧版本目录中的 `pages/*.md`、`images/*`、`documents/*`、`output/*`
2. 在旧版本目录上继续追加本次采集结果
3. 复用旧版本目录中的 `temp/links.json`、`browser_assets.json`、截图或中间结果

### 步骤 1.3 检测页面类型

判断目标网站是静态页面还是需要特殊处理的动态页面。详见 `references/dynamic-page-guide.md`。

**快速判断方法**：
1. 使用 `web_fetch` 尝试获取首页内容
2. 如果返回内容极少（< 500字有效文本）或明显为 JS 渲染框架（React/Vue/Angular），判定为动态页面
3. 动态页面 → 启用 **Agent Browser** 方案（唯一浏览器路径）

## 阶段 2：采集阶段

### 步骤 2.1 首页内容采集

**目标**：获取公司/产品的第一手信息。

#### 静态页面方案

使用 `web_fetch` 获取首页 HTML 并转为 Markdown：

> 将获取的内容保存到 `pages/homepage.md`，供后续分析使用。

记录以下关键信息：
- 公司全称、品牌名称
- 一句话介绍 / Slogan
- 核心产品名称
- 导航栏结构（用于后续链接发现）

#### 动态页面方案

当 `web_fetch` 无法获取有效内容时，按以下优先级尝试：

1. **Agent Browser** — 渲染页面、截图、滚动触发懒加载、提取文本与图片候选
2. **搜索引擎缓存** — 通过 web_search 搜索该公司，从搜索结果摘要中提取信息

### 步骤 2.2 关键页面链接发现

使用 `scripts/discover_links.py` 脚本从首页中发现和分类关键链接：

```text
python <skill-path>/scripts/discover_links.py --url <homepage-url> [--output links.json]
```

脚本会自动按以下优先级分类链接。这里的图片发现仅用于**静态入口补充**，不是最终的动态图片采集主通道：

| 优先级 | 类别 | 说明 | 典型URL模式 |
|--------|------|------|-------------|
| **P0** | 产品页 | 核心产品/解决方案介绍 | `/product`, `/solution`, `/platform` |
| **P0** | 技术页 | 技术架构/白皮书 | `/tech`, `/architecture`, `/whitepaper` |
| **P1** | 案例页 | 客户案例/成功故事 | `/case`, `/customer`, `/story` |
| **P1** | 关于页 | 公司介绍/团队 | `/about`, `/team`, `/company` |
| **P2** | 新闻页 | 新闻/动态 | `/news`, `/blog`, `/event` |
| **P2** | 帮助页 | 文档/帮助中心 | `/docs`, `/help`, `/support` |
| **P3** | 其他 | 联系/招聘等 | `/contact`, `/join`, `/careers` |

输出文件 `links.json` 的关键字段：
- `categories` — 分类后的页面链接
- `image_urls` — 简单图片URL列表（向后兼容）
- **`images`** ⭐ — **带上下文的图片对象数组**（每张图含 `url`, `source_page`, `alt`, `parent_class`, `surrounding_text`, `page_type`, `lazy_loaded`）
- `doc_urls` — 文档URL列表

> 💡 `links.json` 的职责是提供站点入口、部分静态图片 URL 和文档入口。动态页面的图片候选必须通过步骤 2.3 的 Agent Browser 流程补全。

### 步骤 2.3 分页面内容采集

按照 P0 → P1 → P2 的优先级依次采集各页面内容。

每个页面的采集流程：
1. **判断页面类型**（静态/动态）
2. **获取页面内容**
3. **保存为 Markdown 快照**到 `pages/<page_name>.md`
4. **提取页面中的文档链接** → 加入待下载队列
5. **若为动态页或重点页，执行 Agent Browser 采集流程**

**重要**：对于产品页和技术页（P0），必须确保内容完整性。

### 步骤 2.3.5 Agent Browser 动态页面采集

对首页、P0 产品页、P0 技术页和其他重点页面，使用 **Agent Browser** 做真实页面采集。不要为此新增 Python 封装脚本，直接按 agent-native 方式执行。

#### 标准命令序列

```text
agent-browser --session pat-product-research open <page-url>
agent-browser wait --load networkidle
agent-browser set viewport 1920 1080 2
agent-browser screenshot --full --screenshot-dir ./screenshots
```

#### 必做动作

1. 连续多轮滚动，触发懒加载与滚动渲染：
```text
agent-browser scroll down 1200
agent-browser wait 800
```
2. 如页面存在 Tab/Accordion/轮播，点击后重新 `wait --load networkidle`，再重新采集。
3. 使用 `agent-browser eval` 提取图片候选和上下文：
   - `img.currentSrc` / `img.src`
   - `picture source[srcset]`
   - `data-src` / `data-original`
   - `outerHTML`（用于从 `data:image` 懒加载占位图中回溯真实图片 URL）
   - computed style 的 `background-image`
   - 图片附近的 section 标题和正文
4. 使用 `agent-browser network requests` 补充动态加载的图片资源。
5. 对包含“架构 / 技术架构 / 部署架构 / 解决方案 / 功能 / 流程 / 模块”等标题的区域，保存或裁剪截图候选。

#### `browser_assets.json` 约定

Agent Browser 采集完成后，必须整理出 `browser_assets.json`，包含两个顶层数组：

- `images`: 可直接下载的远程图片候选
- `captures`: 本地截图或裁剪图

每个条目必须包含：
- `source_page`
- `capture_type`
- `section_heading`
- `nearby_text`
- `page_type`

可选字段：
- `url`
- `path`
- `alt`
- `title`
- `class_name`
- `id`
- `width`
- `height`

`capture_type` 仅允许以下四种值：
- `dom_image`
- `network_image`
- `section_screenshot`
- `fullpage_screenshot_crop`

### 步骤 2.4 智能图片筛选与下载（v2.5 上下文优先）

> ⚠️ **v2.5 核心理念：先抓到，再按上下文判断**
> - 真实页面采集由 Agent Browser 负责
> - 离线分类只依赖来源页、区域标题、周边文本、截图类型、尺寸和视觉质量
> - 不使用 OCR，不使用 Playwright

#### 调用方式

```text
# 静态发现结果
python <skill-path>/scripts/download_images.py \
  --urls links.json \
  --output-dir ./images

# 浏览器采集结果
python <skill-path>/scripts/download_images.py \
  --urls browser_assets.json \
  --output-dir ./images

# 严格模式
python <skill-path>/scripts/download_images.py \
  --urls browser_assets.json \
  --output-dir ./images \
  --strict
```

脚本输入支持：
- `links.json`
- `browser_assets.json`
- JSON 数组
- 文本 URL 列表
- 本地截图路径

#### v2.5 分类引擎工作原理

```
输入素材 → [1:黑名单排除] → [2:来源页/区域标题关键词匹配] → [3:页面类型加权]
         → [4:截图类型加权] → [5:尺寸/文件大小加权] → [6:视觉质量过滤] → 输出分类
```

| 维度 | 说明 | 技术手段 | 作用 |
|------|------|---------|------|
| **第一关：黑名单排除** | 匹配即跳过 | URL/文件名正则（logo/icon/banner/ad/qr） | 一票否决 |
| **第二关：上下文关键词匹配** | 区域标题、附近文本、alt/title、类名 | 文本匹配 | 直接决定大类 |
| **第三关：页面类型加权** | 来源页是否为产品页/技术页/方案页 | URL 路径推断 | 提升重点页素材 |
| **第四关：截图类型加权** | DOM 图 / 网络图 / 区域截图 / 全页裁剪 | `capture_type` | 提升结构化截图 |
| **第五关：尺寸与大小** | 大图、高分辨率截图优先进入候选 | 像素/体积 | 兜底保留 |
| **第六关：视觉质量分析** | 熵值/边缘密度/颜色数/Banner 形态 | Pillow 像素分析 | 过滤装饰图 |

#### 分类默认规则

- `architecture`
  来源页、标题或上下文包含：架构、系统架构、技术架构、部署架构、拓扑、数据流、architecture、topology
- `feature`
  包含：功能、能力、模块、流程、控制台、仪表盘、feature、workflow、dashboard、console
- `solution`
  包含：方案、解决方案、场景、行业方案、use case、solution、scenario
- `other`
  产品总览、平台总览、生态、矩阵、优势对比等有研究价值但不属于前三类
- `_review_pending`
  重点页面大图、区域截图、上下文疑似有价值但信号不足的素材

#### 输出目录结构

```
images/
├── architecture/       # ✅ 高置信度 — 架构图
├── feature/            # ✅ 高置信度 — 功能图
├── solution/           # ✅ 高置信度 — 方案图
├── other/              # ✅ 高置信度 — 其他有价值图
├── _review_pending/    # 🔍 待审核 — 需要 Agent 视觉复核
└── _download_results.json   # 📋 分类依据、来源元数据和质量指标
```

#### `_download_results.json` 关键字段

同一研究目录内可以先处理 `links.json`，再处理 `browser_assets.json` 或截图清单；脚本必须合并既有 `_download_results.json`，保留每批次的下载、跳过和分类证据，不得用后一次运行覆盖前一次运行。

每张图片的结果应至少包含：

```json
{
  "source_page": "https://example.com/product",
  "capture_type": "section_screenshot",
  "page_type": "product",
  "section_heading": "产品架构",
  "nearby_text": "平台采用分层架构...",
  "category": "architecture",
  "reason": "架构图(架构, 系统架构) +截图候选",
  "quality": { "entropy": 6.2, "edge_density": 0.18, "is_banner_like": false },
  "evidence": { "matched_keywords": ["架构", "系统架构"], "final_score": 12.5 }
}
```

### 步骤 2.4.5 ⚠️ 图片视觉审核（v2.5）

> **触发条件**：下载图片后必须执行。`_review_pending/` 目录必须全量审核；`architecture/`、`feature/`、`solution/`、`other/` 高置信目录也必须逐张或至少按来源页抽样审核。首页轮播图、客户案例图、新闻头图、营销横幅即使被脚本归入高置信目录，也不能直接用于报告。

#### 审核流程

```
对 _review_pending/ 中的每张图片：
  1. 先查看 _download_results.json 中的来源页、capture_type、section_heading、matched_keywords
  2. 用 read_file 工具直接查看图片内容
  3. 判断图片是否展示了真实产品界面、结构化信息图、架构图或方案图
  4. 决策：保留(移到正确分类) / 删除

对高置信分类目录：
  1. 检查 `architecture/` 是否只包含架构、拓扑、数据流、模块关系或部署图
  2. 检查 `feature/` 是否只包含产品界面、控制台、仪表盘、配置面板、数据表格或功能流程
  3. 检查 `solution/` 是否只包含场景方案、行业方案、方案架构或安全运营流程
  4. 检查 `other/` 是否仍具备研究价值，例如产品总览、能力矩阵、对比图或生态图
  5. 将客户建筑照、车辆照片、监管门头、活动照片、抽象 API 装饰、纯营销横幅删除或移入 `_review_pending/` 重新判断
```

#### 审核判断标准

**保留条件（满足任一即可）**：

- 区域标题或图中内容明显对应架构、功能、方案
- 图片展示真实产品界面、配置面板、数据表格、仪表盘
- 图片是结构化信息图：流程图、拓扑图、模块图、对比图
- 图片来自重点页面且视觉内容明显与产品能力相关

**删除条件（匹配即删除）**：

- slogan/banner/营销主视觉
- 抽象插画、办公摆拍、团队照片
- logo/icon/二维码/社交媒体素材
- 与产品功能无关的企业介绍图

### 步骤 2.5 文档资源下载

使用 `scripts/download_docs.py` 脚本下载文档资源：

```text
python <skill-path>/scripts/download_docs.py \
  --urls <docs_json_file> \
  --output-dir ./documents \
  --retries 1
```

支持格式：PDF / Word(.doc/.docx) / PPT(.ppt/.pptx) / Excel / Markdown / TXT

自动分类存放：白皮书(`whitepaper/`) / 案例(`case/`) / 手册(`brochure/`) / 其他(`other/`)

下载完成后必须查看 `documents/_download_results.json`：
- `summary.failures` 记录仍失败的文档 URL、失败原因和尝试次数。
- 如果关键 Datasheet、白皮书、案例 PDF 失败，应重试；仍失败时在报告信息局限中写明失败 URL 和替代来源。

### 步骤 2.6 补充信息搜索

当官网信息不足时，通过 web_search 补充：
- `<公司名> 产品介绍` / `<公司名> 融资 创始人 团队`
- `<公司名> 竞品 对比` / `<公司名> 案例 客户`

## 错误处理

### 网络问题

| 场景 | 处理策略 |
|------|---------|
| 首页无法访问 | 告知用户并建议检查 URL；可通过搜索引擎尝试获取缓存信息 |
| 部分页面无法访问 | 记录失败 URL，继续处理其他页面；在报告中注明信息可能不全 |
| 图片/文档下载失败 | 重试 1 次；仍失败则跳过，记录失败清单 |

### 内容质量问题

| 场景 | 处理策略 |
|------|---------|
| 官网内容过少 | 通过 web_search 大量补充公开信息；在报告中注明数据来源 |
| 动态页面无法渲染 | 尝试搜索引擎快照；告知用户限制并在报告中说明 |
| 无法判断竞品 | 基于产品定位推测潜在竞品，明确标注「推测」 |

### 安全限制

- ❌ 不访问/下载可执行文件
- ❌ 不跟踪 tracking pixel / beacon
- ⚠️ 单文件 ≤ 100MB
- ⚠️ 尊重 robots.txt
