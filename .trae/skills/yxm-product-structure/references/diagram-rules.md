# 图形规则

最终产品结构说明书必须包含三张图：

```text
核心对象关系图
产品模块架构图
核心业务流程图
```

三张图必须从同一份结构状态派生：

```text
核心对象关系图 <- objects + relationships
产品模块架构图 <- modules + upstream/downstream + external dependencies
核心业务流程图 <- actions + flows + decisions + exceptions
```

如果结构状态变化，先标记受影响图为 `stale` 或 `needs_redraw`，再更新图。禁止只改正文不改图，也禁止只改图不改结构状态。

## 生成顺序

每张图必须按这个顺序生成：

```text
图规格 -> Mermaid -> 三图质量门
```

图规格必须简短写在 Mermaid 前：

| 字段 | 要求 |
|---|---|
| 回答的问题 | 一句话说明本图解决什么问题 |
| 数据来源 | `objects` / `modules` / `actions` / `flows` 中的哪一组 |
| 允许节点 | 本图可以出现的节点类型 |
| 禁止节点 | 本图不能混入的节点类型 |
| 最大节点数 | 超过就合并，不硬塞 |
| 颜色语义 | 颜色代表业务含义，不代表好看 |

## 三图边界

| 图 | 只回答 | 允许 | 禁止 | 默认上限 |
|---|---|---|---|---|
| 核心对象关系图 | 核心对象如何发生关系 | 角色、业务对象、判断材料、判断对象、配置对象、结果承接对象、外部依赖 | 模块、页面、流程步骤、技术服务、字段、过程日志 | 8-12 节点 |
| 产品模块架构图 | 核心模块如何交接 | 核心模块、明确外部依赖、必要结果承接能力 | 配置对象、算法、AI 子能力、人工动作、页面入口、数据表 | 4-7 模块 |
| 核心业务流程图 | 核心场景如何从触发到闭环 | 触发、动作、判断、异常、人工确认、结果沉淀 | 对象关系复刻、模块架构复刻、无状态变化的展示页 | 10-16 节点 |

## 三图质量门

每张 Mermaid 后必须自检：

```text
内容对题：是否只回答本图的问题。
边界干净：是否混入禁止节点。
关系有效：每条边是否表达关系、交接或状态流转。
复杂度受控：节点数是否未超过上限。
样式可读：节点短、方向清楚、颜色有图例且同色不多义。
结构一致：是否与 Canonical Structure、模块卡片、本轮结构检查一致。
```

不通过时：

```text
对象图混入模块/流程 -> 回到 objects 重画。
模块图混入配置/AI子能力/人工动作 -> 回到 modules 重画。
流程图混入对象关系/模块结构 -> 回到 actions 和 flows 重画。
节点过多 -> 合并同层节点，次要内容放图后说明。
```

## 核心对象关系图

回答：

```text
这个产品世界里有哪些核心对象，它们如何互相作用？
```

应表达：

```text
用户 / 角色
业务对象
过程对象
判断对象
沉淀对象
外部依赖
```

三张必备彩色图必须使用 Mermaid `flowchart`，并使用 `classDef` 和 `class` 标注颜色语义。

`erDiagram` 只能作为可选补充图，不能算作三张必备语义彩色图之一。

## 产品模块架构图

回答：

```text
产品由哪些能力模块组成，模块之间如何连接？
```

应表达：

```text
核心链路模块
支撑能力模块
外部依赖
反馈闭环
上游 / 下游关系
```

这张图是产品能力架构，不是技术服务架构。研发可以从这里继续拆技术边界，但本图不直接规定微服务、数据库或部署方式。

## 核心业务流程图

回答：

```text
一个核心业务场景从触发到闭环，用户、系统、Agent 和人工决策如何一起走？
```

应表达：

```text
触发事件
用户动作
系统动作
Agent 动作
人工确认
决策分支
处置动作
审计 / 沉淀
异常回路
```

## 颜色语义规则

三张图必须使用颜色区分不同概念类型。颜色不是装饰，而是语义编码。

不要预设固定颜色含义。每个产品的对象、角色、流程和模块类型不同，颜色语义必须根据本次产品结构现场定义。

必须满足：

1. 每张图必须先声明颜色图例。
2. 同一张图中，同一种颜色只能代表一种含义。
3. 同一种概念类型在同一份文档的多张图中尽量使用同一种颜色。
4. 如果同一颜色在不同图中含义不同，必须明确说明，避免读者误解。
5. 不得为了美观临时换色。
6. 不得用颜色表达“好看”“高级”“重点”，除非本图明确把颜色定义为优先级或风险等级。
7. 图例中的颜色含义必须来自本产品本身，而不是套用固定模板。
8. 颜色分类数量要克制。通常 4-7 类足够；超过 8 类说明分类可能过细。

## 可选语义轴

根据图的目的选择一种主语义轴，不要在同一张图里混用多套颜色逻辑。

核心对象关系图可以按：

```text
角色类型
业务对象类型
生命周期对象
判断对象
外部依赖
```

产品模块架构图可以按：

```text
能力层级
模块责任类型
用户侧 / 系统侧 / 组织侧
核心链路 / 支撑能力 / 外部依赖
```

核心业务流程图可以按：

```text
用户动作 / 系统动作 / 人工决策 / 自动化动作
正常路径 / 异常路径 / 审计沉淀
触发 / 判断 / 处置 / 归档
```

## 图例格式

每张图在 Mermaid 代码块前必须声明本图的颜色语义轴，并写清图例：

```text
颜色语义轴：{本图按什么维度设色}
颜色语义：
- {颜色名或色值}：{本图中代表的语义}
- {颜色名或色值}：{本图中代表的语义}
- {颜色名或色值}：{本图中代表的语义}
```

## Mermaid 要求

三张必备图必须使用 `flowchart`，并使用 `classDef` 和 `class` 明确标注颜色语义。

不能只依赖节点文字或线条方向表达分类。

禁止：

```text
无图例的彩色图
同色多义
同义多色，除非说明原因
颜色只为美观服务
套用和当前产品无关的固定配色表
```
