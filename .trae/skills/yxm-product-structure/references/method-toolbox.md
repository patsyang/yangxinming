# 方法工具箱

方法论是工具，不是最高原则。它们帮助建模，但不能替代产品判断。

## Opportunity Solution Tree

用于机会与产品概念前置判断，防止直接跳功能。

结构：

```text
Desired Outcome
-> Opportunities
-> Solutions
-> Experiments
```

使用时机：

```text
用户给的是模糊产品方向
团队已经跳到某个功能，但问题还没定
多个方案争夺同一个产品概念
需要判断这个产品到底围绕哪个 outcome 成立
```

输出重点：

```text
单一 desired outcome
3-7 个 opportunity
每个 opportunity 的 solution 候选
最便宜的验证实验
哪些 solution 只是功能冲动
```

## User Story Mapping

用于把产品想法落到用户行动链，防止从菜单列功能。

结构：

```text
Activity
-> Step
-> Task
-> Release Slice
```

使用时机：

```text
需要知道用户从开始到闭环怎么走
需要找 MVP 最短闭环
需要从行动链里长出能力地图
```

注意：

```text
Activity 不是 feature。
Step 不是页面。
Task 不是开发任务。
Release slice 不是 P0/P1 功能清单。
```

## DDD

用于核心对象、边界和技术可继承结构。

借用概念：

```text
统一语言
核心域
限界上下文
领域事件
聚合
上下文映射
```

使用时机：

```text
核心对象不清
模块边界混乱
业务流程里有关键状态变化
外部系统关系复杂
产品模块需要向技术边界传递
```

不要把 DDD 变成技术术语表。这里的目标是让产品结构更硬，不是直接设计领域模型代码。

## Shape Up 的 shaping / slicing

用于控制范围和切片。

借用思想：

```text
先 shape，再 build
先定边界和 appetite，再拆任务
slice 是可交付闭环，不是功能列表
```

使用时机：

```text
MVP 过大
模块范围过散
产品想法还只是愿望，没有形状
```

## 模块边界判断

一个模块必须回答：

```text
它围绕哪个对象？
它服务哪个用户行动？
它把对象从什么状态推到什么状态？
它的输入是什么？
它的输出是什么？
它和哪个模块交接？
用户为什么会把它理解成一个独立能力？
研发为什么能继承它作为技术边界线索？
```

回答不了，就不是模块。

空模块坏味道：

```text
用户管理
权限管理
报表管理
配置管理
系统管理
```

这些词不是永远不能用，但如果它们不能说明对象、行动、状态变化和边界，就是空模块。

## MVP 闭环判断

MVP 不是 P0 功能列表。

MVP 是：

```text
一条能闭环的最短用户行动链。
```

MVP 必须说明：

```text
闭哪条核心业务链
包含哪些模块的最小能力
哪些模块只做最小版本
哪些模块暂不做
哪些自动化先人工替代
哪些外部系统先手工接入
```
