# Review Checklists

## 产品负责人检查

```text
产品母题是否一句话能说清？
目标用户是否具体？
核心场景是否能复现？
用户行动链是否从真实行动出发？
MVP 是否闭合一条完整业务链？
非目标是否足够清楚？
```

## 研发总监检查

```text
每个模块是否有清晰输入和输出？
模块边界是否能被研发继承？
模块之间的交接是否明确？
哪些环节同步，哪些异步？
哪些需要人工，哪些可自动化？
哪些对象和状态必须落到系统里？
```

## CTO 检查

```text
产品结构是否能支撑后续技术架构？
核心对象是否稳定？
模块边界是否避免把技术组件伪装成产品模块？
外部依赖是否被标出？
审计、权限、数据、事件、Agent 编排等关键风险是否有落点？
技术落地映射是否越界到具体实现？
```

## 架构师检查

```text
对象关系图、模块架构图、业务流程图是否来自同一套结构状态？
图和模块卡片是否一致？
状态流是否完整？
异常路径是否出现？
哪些模块可能成为服务边界候选？
哪些事件需要留痕？
```

## 三张图同步检查

```text
核心对象关系图是否包含最终对象模型里的核心对象？
产品模块架构图是否包含最终模块卡片里的所有模块？
核心业务流程图是否覆盖 MVP 核心链路？
三张图是否都有颜色语义说明？
必备三张图是否都使用 flowchart + classDef/class？
是否存在 stale / needs_redraw 未处理？
```

## MVP 检查

```text
MVP 是否是一条可闭环的用户行动链，而不是 P0 功能列表？
MVP 是否说明闭哪条核心业务链？
MVP 是否明确包含哪些模块的最小能力？
MVP 是否说明哪些模块只做最小版本、哪些暂不做？
MVP 是否说明哪些自动化先由人工替代？
MVP 是否说明哪些外部系统先手工接入？
```

## 最终交付检查

```text
一句话能说清产品母题。
核心对象不滥。
每个模块都能挂回用户行动链。
每个模块都有状态变化、输入、输出和边界。
三张图能互相解释，而不是各画各的。
颜色语义稳定，图例清楚。
MVP 是一条闭环路径，不是功能清单。
研发总监和 CTO 能继续向下拆技术架构，而不是重新猜产品结构。
不做什么比做什么更清楚。
```
